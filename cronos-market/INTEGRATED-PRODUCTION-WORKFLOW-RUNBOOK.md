## Multi-collection lineage (Phase5)
Owned production now accepts collectionLineages in addition to the existing singular lineagePath/lineageDigest mode. Modes are mutually exclusive. The CLI form is an array of exact `{path,reviewedHash}` descriptors, one for every selected collection (up to16). The API form is exact `{manifest,reviewedHash}` entries. Bindings must cover all selected collections exactly once, with no duplicates or foreign collection. Each exact input image must match its reviewed paired-capture manifest/digest/checkpoint. Existing common checkpoint and source-acceptance checks remain required. Summaries are sorted by address and retained as collectionRebuildLineages in evidence/receipt; singular ownership and selected marketplace lineage remain distinct.

Ordering is now ASCII lexical rather than host-locale-dependent for produced collection/candidate/proof arrays. This reduces cross-host ordering differences; changing input annotations/source artifacts still creates a different request pin.

## Shared production config (Phases5/8)
`server/owned-production-config.js` now provides one request loader for the CLI and maintenance runtime. It implements exact config keys, mutually exclusive legacy/v2 accounting, paired optional pins, protected absolute regular single-link files, O_NOFOLLOW at the final component, no group/other file permissions, post-read change checks and aggregate32MiB input budget. Individual image8MiB, timestamp2MiB, config/acceptance/lineage64KiB bounds remain. This deliberately tightens the earlier CLI's group-readable admission; operator files must be private, not silently accepted as secret-safe.

The requestDigest canonically commits admitted options and the output directory, excluding source pathnames but including the actual loaded source documents/pins. Runtime fingerprint commits the runtime config/requestDigest. No provider or credential/configuration is chosen automatically. The existing owned:produce command uses this loader; no new activation environment is introduced.

## Durable private production (Phases5/7)
`server/owned-production-workflow.js` replaces the previous non-resumable three-file CLI writer. It validates all current source acceptances and producer semantics before creating output. An exclusive private directory contains only intent.json, evidence.json, dataset.json, receipt.json. Unknown files (including documentation) cause refusal, **not deletion**. Existing legacy three-file output remains inspectable, but is not silently adopted as a resumable intent-based workflow.

The immutable intent pins requestDigest and generation time. Retry regenerates exactly the same output using that time, while revalidating source acceptance and dataset expiry against real current time; a frozen generation time cannot revive expired source approval. Complete matching files are reused. Missing files are written exclusively, with receipt last. Different/truncated/unsafe files require review and are never overwritten or removed. Crash after receipt write but before job finish can recognize already-produced content. Changed source/request cannot be resumed into an old directory.

Every written file is fsynced; containing directory entries are fsynced and directory creation syncs the parent. These improve local durability but do not make a multi-file transaction, prevent all filesystem races or guarantee remote-filesystem crash semantics. Unsupported directory sync fails explicitly and leaves evidence for inspection. Trusted parent directories/cooperative writers remain necessary.

Raw evidence and dataset remain at most1MiB each; total intended workflow bytes at most3MiB. Before missing-file writes, statfs headroom must cover missing bytes plus16MiB. This is a point-in-time observation, not a reservation against unrelated writers, per-host quota or recurring retention/capacity service. Existing complete artifacts may be inspected/reused without consuming new file space. No artifacts, snapshots or MD/TXT are deleted.

The existing inspect action requires a reviewed raw receiptSha256, exact evidence/dataset byte pins, current dataset shape/expiry, and (for workflow receipts) matching intent/request/generation time. It performs no RPC, source renewal or writes. Production still stops at private artifacts, verified:false/activated:false, with no live pointer/config changes.

## Receipt acquisition integrity (Phases6/8)
Shared receipt-backfill now validates the complete advertised transaction list before and after every slice, not just the block hash. Transaction identities are normalized before duplicate checks. All receipt logs are checked before filtering by destination/topic: status/failed-receipt rules, address/topics/data shape, transaction/block/index binding, contiguous available log positions and byte/count bounds. Topic matching is case-normalized. Invalid irrelevant logs cannot bypass validation merely because they do not match the requested collection.

New scans retain nextLogIndex and observedLogBytes. Node collection staging and the complete-block reader persist/propagate slice.scan. Worker collection staging already consumes slice.scan and therefore retains it without schema changes. Legacy pending scans without the fields are admitted with continuity beginning at their first newly observed log, not retroactively claimed as checked. Other Worker receipt tables that persist only a transaction cursor continue to enforce slice-local checks; whole-block cumulative continuity across those persisted boundaries is still incomplete. No migration or destructive reset is performed.

Limits remain explicit: at most20000 advertised transactions in the shared resumable scan, per receipt/slice8192 observed logs, log position below20000, carried byte count8MiB, each log data up to8KiB,1..8 receipts per slice. Existing independent complete-block readers still retain their256-transaction admission and8192-selected-log/8MiB limits. Overflows fail rather than publishing a partial checkpoint. These changes do **not** solve oversized ERC1155 expansion, all truncation cases, complete-block density or receipt-trie proof; a consistently omitted final receipt/log or transaction list can still evade provider-response checks. Complete acquisition remains an open Phase6 responsibility.
